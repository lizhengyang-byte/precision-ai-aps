# 03 · 系统架构

## 一、总体分层

```
看板（原生 JS + SVG）
        ↓ REST/JSON
API 层（FastAPI：主数据 / 排产 / 版本 / 事件 / 报工 / AI）
        ↓
业务层（services：组装 Problem、版本管理、差异对比、进度汇总）
        ↓
引擎层（CP-SAT 求解器 / 启发式降级） + AI 决策层（策略、雷达、NLU、可选 LLM）
        ↓
数据层（SQLAlchemy + SQLite / PostgreSQL）
```

## 二、目录结构

```
app/
  config.py          # 环境变量、默认求解时长
  database.py        # 引擎/会话/建表
  models.py          # 设备、人员、产品、工艺、订单、版本、任务、报工、事件
  services.py        # Problem 组装、排产入口、版本序列化、diff、进度
  seed.py            # 演示车间数据（5 产品 / 22 工序 / 9 设备 / 8 人 / 12 单）
  main.py            # FastAPI 入口 + 启动自动排产
  engine/
    model.py         # Problem / Task / WorkCenter / Operator / FixedAssignment
    calendar.py      # 班次日历：工时↔自然时间、班次窗口约束
    cpsat_solver.py  # 有限产能排产模型
    heuristic.py     # 列表调度降级（ORTools 不可用时）
    metrics.py       # KPI：拖期、按期率、利用率、瓶颈、在制
  ai/
    strategy.py      # 策略推荐（可解释因子评分）
    insight.py       # 交付风险雷达 + 瓶颈排队估计 + 技能缺口
    nlu.py           # 中文调度指令解析
    llm.py           # 可选大模型润色（OpenAI 兼容）
  api/routes.py      # 全部 REST 接口
  static/            # 看板 index.html / styles.css / app.js
scripts/demo.py      # 命令行演示（可导出甘特图）
tests/               # 引擎 / API / AI 测试
docs/                # 本文档集
```

## 三、核心数据模型

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| Machine | code, machine_type, precision_grade, efficiency, status | 设备能力与精度 |
| Worker | code, name, level, skills(JSON), shift | 技能矩阵 |
| Product / Routing | code, family, tolerance_um; seq, std_minutes, required_level, min_precision | 工艺路线 |
| Order | code, qty, due_date, priority, release_at, status | 交付要求 |
| ScheduleVersion | strategy, solver, metrics(JSON), parent_id | 排产快照 |
| Assignment | version_id, task_key, machine, operator, start, end, good_qty | 工序任务 |
| ProgressReport | assignment_id, good_qty, scrap_qty | 报工流水 |
| EventLog | kind, payload, start, end, active | 故障 / 缺勤等扰动 |

时间统一用“工时坐标”（work minutes）存储，展示时经 `ShopCalendar` 转为自然时间，避免班次/周末造成口径混乱。

## 四、API 一览

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | /api/meta | 能力与策略清单 |
| GET | /api/master | 设备/人员/产品/订单主数据 |
| POST/PATCH | /api/orders | 新建 / 修改订单 |
| POST | /api/schedule/solve | 排产（strategy=auto 或指定） |
| GET | /api/schedule/current | 当前版本 + 任务 + 进度 |
| GET | /api/schedule/versions/{id} | 历史版本 |
| GET | /api/schedule/diff | 两版本逐工序差异 |
| GET | /api/kpi | KPI + 订单交付表 |
| GET | /api/ai/advice | 策略建议 + 解释因子 |
| GET | /api/ai/radar | 交付风险雷达 |
| POST | /api/ai/chat | 中文指令解析与执行 |
| POST | /api/events | 登记扰动并触发重排 |
| POST | /api/progress/report | 工序报工 |

## 五、关键设计选取

- **版本化而非就地修改**：每次排产生成新版本，保留 parent_id，天然支持回滚与追责。
- **冻结机制**：已开工/已完工工序作为 FixedAssignment 进入模型，保证重排不扰动现场。
- **求解器可降级**：ORTools 缺失或超时时自动回退到列表调度启发式，保证服务可用。
- **无前端构建链**：原生 JS + SVG，现场断网时单机部署即可打开，降低维护成本。
