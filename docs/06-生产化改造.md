# 06 · 生产化改造记录（v1.0 → v1.1）

原型能算出一版计划，不等于车间敢用。对照开源 MES/APS 的落地经验（frePPLe 的计划版本、OpenMes 的工单闭环），v1.1 补齐的是“责任、边界与可运维性”。

## 一、改造清单

| 能力 | v1.0 | v1.1 |
| --- | --- | --- |
| 账号与权限 | 无，任何人可改计划 | PBKDF2 口令 + JWT；admin/planner/operator/viewer 四角色；登录失败 5 次锁定 60 秒 |
| 计划下发 | 任何重排立即生效 | 草稿 → 提交 → 审批 → 发布；重复发布被状态机拒绝 |
| 历史版本 | 可查，不可回退 | 回滚以“克隆新版本”实现，历史版本永不篡改 |
| 审计 | 无 | 登录、发布、回滚、建号等写操作全量落 `audit_logs`，含人、角色、对象、参数、IP |
| 计划稳定性 | 仅冻结已开工 | 冻结窗口默认 120 分钟：即将开工的工序一并锁定，避免班组长刚到岗计划就变 |
| 逾期订单 | 固定优先级权重 | 超期越久权重越高（每 2 小时 +1，上限 +30），老单不会被无限推后 |
| 执行层 | 甘特图 + 报工 | 当日派工单（按设备排序、标换型/冻结）、OEE、7 天产能负荷 |
| 可观测性 | 无 | `/healthz`、`/readyz`、`/metrics`、请求 ID、结构化访问日志 |
| 部署 | SQLite + 单容器 | PostgreSQL 16 + 非 root 多阶段镜像 + Compose 健康检查 |
| 质量门禁 | 本地 pytest | GitHub Actions：ruff + 20 项测试 + 镜像冒烟 |

## 二、计划状态机

```text
ok ──submit──▶ submitted ──approve──▶ approved ──publish──▶ published ──▶ archived
                   │                        ▲
                   └────reject──▶ rejected ─┘（可重新提交）

任意历史版本 ──rollback──▶ 新版本（status=published，parent_id=当前版本）
```

规则：`planner/admin` 可提交与审批；`planner/admin` 发布 `approved` 版本；`admin` 可直接发布 `submitted` 版本（应急通道，留审计）。发布时旧的 `published` 自动转 `archived`，避免双基线。

## 三、安全模型

- 口令：PBKDF2-HMAC-SHA256，26 万次迭代，盐随机 16 字节，散列串自带参数便于轮换；
- 令牌：HS256 JWT，默认 12 小时过期；`AUTH_SECRET` 未配置时生成临时密钥并告警（重启即失效）；
- 传输与响应：统一 `X-Content-Type-Options`、`X-Frame-Options`，CORS 由 `CORS_ORIGINS` 控制；
- 初始管理员：启动时若账号表为空则创建，标记 `must_change_password`，前端登录后提示改密；
- 审计留存：`audit_logs` 可按时间/动作检索，建议按季度归档到对象存储。

## 四、OEE 口径（当前版本）

`OEE = 可用率 × 性能率 × 良品率`

- 可用率 = 1 − 故障停机分钟 / 有效班次分钟（每日 12 小时、周日休息）；
- 性能率 = 计划占用分钟 / 有效班次分钟（上限 1）；
- 良品率 = 良品数 /（良品数 + 报废数）。

限制：性能率目前用“计划占用/有效班次”近似，尚未接入设备实际节拍；接入 OPC UA/MQTT 后应替换为“标准工时 × 产量 / 实际运行时间”。这一口径已在接口 `basis` 字段中显式说明，避免误读。

## 五、仍然存在的边界

1. 换型时间仍是路由内的固定装夹时间，未做 sequence-dependent setup；
2. 订单不拆批，超大单会长时间占用瓶颈设备；
3. 物料齐套只体现为订单下达时间，未接库存；
4. 求解为单进程同步调用，超过 200 道工序建议拆分产品族分窗求解或改为任务队列；
5. SQLite 适合单车间（<20 并发），多车间请直接用 PostgreSQL。

这些边界已写入路线图，不在文档里含糊带过。
